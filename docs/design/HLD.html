Goblin Toolbox — high-level design

Overview

Goblin Toolbox is a set of tools grouped into vaults. Each tool has a UI and an API. The architecture uses micro-frontends for the UI and microservices for the API, but everything is deployed as one.

  • Micro-frontends with Module Federation. The Host is the only app users open. Each tool's UI is a remote: a separate static build that the Host loads at runtime and shows in the tool page. React, React Router, i18next and the UI kit are shared, so they load only once.
  • One microservice per tool. Each tool's API is its own Express service in its own Vercel Function, with its own memory and time limit. A heavy tool does not slow down or bloat the others. The UI remote calls it with fetch over HTTPS with JSON, through Edge on the same domain (no CORS). Both sides share the tool's Zod schemas.
  • Tool = UI remote + API service. Both live in one tool package and always change together.
  • Static catalog. Each tool has a manifest. The Host's vault config says which tool is in which vault. A build step merges them into catalog.json. Adding a tool does not change Host code.
  • One deployment. One Vercel project with Vercel Services. Every service builds on its own, but all of them ship and roll back together. Edge sends each path to the right service.

Trade-offs

Area What we gain What it costs
Runtime resources Each tool API has its own memory, duration and bundle; a heavy tool does not slow or bloat light ones. 2N + 1 services; the route table and total build time grow with every tool.
Adding a tool A manifest and a vault entry; the Host's code does not change. A build-time catalog step and a manifest contract to keep stable.
Boundary The Host never imports tool code at build time; tools are isolated units. Shared-dependency mismatches surface as runtime errors, not build errors.
Shared dependencies React, router, i18next and the UI kit are loaded once and shared. Upgrading any of them means upgrading the Host and every remote together.
Deploy and rollback One atomic deployment; Host, remotes and APIs never drift apart. Module Federation's main benefit, independent deploys, is not used yet.
Performance Tool code loads only when its page opens. Two extra requests (catalog.json, remoteEntry.js) before a tool renders.
Styling Tools share design tokens through the UI kit. Remote CSS shares the Host page and needs scoping rules.
Development and tests Each tool's UI and API can be built and unit-tested on its own. End-to-end tests and local runs need the Host, remotes and APIs together.
Platform Routing, rollback and previews stay in one Vercel project. Vercel Services is in beta; Hobby limits on services and build time must be verified.
